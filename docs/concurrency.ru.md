# Обработка concurrency

[English version](concurrency.md) · [Вернуться к README](../README.ru.md)

## Проблема

Два студента могут прочитать одну свободную сессию и почти одновременно попытаться её забронировать. Без concurrency control более поздняя запись могла бы затереть предыдущую или привести к некорректному результату.

## Текущий подход

`Session.Version` настроен как concurrency token в EF Core. PostgreSQL и EF Core обнаруживают, что строка изменилась после загрузки, и выбрасывают `DbUpdateConcurrencyException`.

Booking handler выполняется внутри именованного Polly `ResiliencePipeline`:

1. Загружает актуальное состояние сессии.
2. Повторно проверяет доменные правила через `Session.Book`.
3. Пытается сохранить изменение.
4. При `DbUpdateConcurrencyException` очищает устаревший EF Core change tracker и пробрасывает исключение дальше.
5. Polly повторяет всю операцию, поэтому состояние загружается заново и бизнес-правила проверяются ещё раз.

Pipeline использует ограниченное число повторов, exponential backoff, jitter и cancellation token запроса.

## Что повторяется

Pipeline обрабатывает только `DbUpdateConcurrencyException`.

Без retry сразу возвращаются:

- неаутентифицированный пользователь;
- отсутствующая сессия;
- ошибка валидации;
- уже забронированная или отменённая сессия;
- уже начавшаяся сессия.

Так обычные доменные конфликты не маскируются под временные инфраструктурные ошибки.

## Результат конкурирующих бронирований

После успешного сохранения одного бронирования следующая попытка загружает изменённую строку. Доменная модель видит, что сессия уже не свободна, и возвращает конфликт вместо перезаписи успешного бронирования.

## Ближайшие улучшения

- завершить отдельные тесты выполнения и исчерпания retry;
- покрыть реальный сценарий конкурентного бронирования;
- применять тот же подход к отмене только там, где повтор семантически безопасен.
